# AI 面试陪练：需求分析与调研方案

> 状态：挑战项目早期方案。本文中的调研结论和样例数据均为合成/模拟内容，不能对外表述为真实受访者数据。

## 1. 研究目标

验证三个假设：

1. 本科生在准备实习/保研面试时，最大的缺口不是“没有题目”，而是缺少结合目标岗位和个人经历的练习路径。
2. 结构化、引用原回答证据的反馈，比泛泛的参考答案更有价值。
3. 压力面、技术面、行为面等不同场景需要不同的提问策略和反馈标准。

## 2. 问卷（预计 5 分钟）

### 开场与同意

本问卷面向近 12 个月内准备过实习、校招或保研面试的学生，预计用时 5 分钟。问卷不收集姓名、联系方式或真实简历；请使用概括性描述，不要填写身份证号、手机号、公司内部资料等敏感信息。数据仅用于产品研究和原型改进。提交即表示同意将匿名回答用于上述目的；不同意可随时退出。

## 3. 真实调研执行规范

- 先完成 5–8 个半结构化访谈，再扩大问卷样本。
- 记录受访者类型、招募渠道、日期和原始问题，不记录姓名和联系方式。
- 所有公开题目保存来源 URL、发布日期/抓取日期、许可证或使用条款。
- 简历、面试复盘和回答必须脱敏；不抓取需要登录或明确禁止自动化采集的站点。
- 对外展示时区分 `observed`（真实且有来源）与 `synthetic_mock`（模拟）。

## 4. 合成数据的使用方式

本项目可用合成数据验证问卷分析、GraphRAG 检索和页面流程，但必须在 README、Memo 和演示中写明“合成数据/模拟调研”，不能说成已收集的真实用户数据。真实结论应等问卷回收后再替换。

## 5. 真实面试数据的采集路线

先建立“来源台账”，再进入 GraphRAG，不要直接把网页文本当成事实：

1. **公开许可内容**：优先使用明确标注许可证的 GitHub 题库、开放课程和公开文档。
2. **官方内容**：公司招聘官网、技术博客、面试准备指南，用于确认岗位技能和面试环节，不把宣传性内容当作真实频次。
3. **公开讨论内容**：只采集无需登录且允许再利用的公开讨论；保存原始 URL、访问日期和页面条款，禁止绕过登录、反爬或付费墙。
4. **技能知识库**：使用 O*NET/ESCO 等公开职业技能分类补充 `Skill` 节点，和面试题来源分开标记。

每条题目建议保存：`source_id`、`url`、`title`、`published_at`、`accessed_at`、`license`、`role`、`process_type`、`question`、`skills`、`difficulty`、`pii_redacted`、`source_confidence`。来源不明的题目只能作为低置信度候选，不能展示“高频”标签。

## 6. 合成样例的演示性洞察

随附的 15 条问卷回答仅用于测试分析流程：

- 15/15 的模拟受访者表达了较高尝试意愿（4 或 5 分），但这不是市场需求证明。
- 8/15 将当前反馈满意度评为 2 分，说明“反馈具体性”可以作为待验证假设。
- 反复出现的主题是：JD/简历匹配、引用原回答证据、连续追问和压力面适应。

这些数字只能写成“模拟样例观察”，不能写成“调研发现”或“用户调研证明”。

## 7. 初版产品需求

### P0：挑战当天必须完成

- 输入目标岗位、JD 和个人经历摘要。
- 按岗位技能和面试类型生成一道问题。
- 用户进行文字回答。
- 输出引用回答原句的结构化反馈。
- 提供“再答一次”和“下一题”。
- 支持示例数据一键体验。
- API key 只在服务端保存，公网 URL 可访问。

### P1：有余力再做

- 技术面/行为面/压力面三种模式。
- 反馈维度随面试类型变化。
- 会话结束后的薄弱项总结。
- 本地保存最近一次练习记录。

### P2：挑战后迭代

- 语音回答和语气分析。
- 更完整的岗位知识图谱。
- 多轮压力面角色扮演。
- 长期能力趋势和个性化训练计划。

## 8. GraphRAG 方案（先做最小闭环）

### 节点

- `Job`：岗位、公司、岗位级别
- `Skill`：技能、知识点、能力项
- `InterviewStage`：技术面、行为面、压力面等
- `Question`：题目、追问、难度、考察目标
- `Rubric`：评分维度和评价标准
- `UserEvidence`：用户的项目、技能和回答证据
- `Source`：题目来源、时间、许可证、可信度

### 关系

- 岗位 `requires` 技能
- 题目 `tests` 技能
- 题目 `used_in` 面试环节
- 题目 `has_follow_up` 追问
- 题目 `scored_by` 评分标准
- 用户经历 `supports` 技能
- 题目 `cited_from` 来源

### 检索流程

1. 抽取 JD 和个人经历中的技能、项目、岗位关键词。
2. 先用图关系筛选“岗位要求 + 面试环节 + 难度”。
3. 再用向量检索找语义相近的题目和评分标准。
4. 用来源可信度、时间和重复度重排。
5. 生成题目时返回“匹配了哪些技能、为什么问”。
6. 反馈时只允许引用用户提供的证据，缺失信息明确标记未知。

挑战当天不必实现完整 GraphRAG 平台；可以用 JSON/SQLite 模拟图谱，先展示“JD/经历 → 技能 → 题目 → 反馈”的可解释链路。

## 9. 验证指标

- 至少 5 名目标用户完成一次测试。
- 4/5 用户可以独立完成一轮练习。
- 3/5 用户认为反馈比普通 ChatGPT 更具体。
- 每条反馈至少包含一条原回答证据和一条可执行改进建议。
- 连续 5 次请求无崩溃，API 失败时有明确提示。

## 10. TechMatch 经验复用映射

TechMatch 项目中已有几块能力可以直接借鉴，但挑战当天应只抽取最小必要部分：

- `backend/services/file_extract_service.py`：复用文件/文本抽取思路，输入先统一成干净的 JD 与经历文本。
- `backend/services/smart_match_service.py`：复用候选召回、结果排序和 AI 评分的模式，改成“岗位技能 → 面试题”匹配。
- `backend/services/graph_search_service.py`：复用检索结果格式化、来源路径映射和可解释推荐思路。
- `backend/utils/prompt_loader.py`：复用外置 Prompt 模板，分别维护出题、追问和反馈模板。
- `benchmarks/` 下的 TSV：复用评测集/查询变体的思路，建立 5–10 组固定 JD-题目匹配样例。
- 前端文件上传和会话状态：复用已有交互结构，但删除本项目不需要的多模式和复杂附件逻辑。

不要把 TechMatch 的科研检索、长流程缓存和多类型资源查询整体搬过来；本项目的可展示价值是一个学生能完成的面试训练闭环。

## 11. 多场景与算法题扩展

### 面试场景统一接口

所有场景共用 `Session`，只替换 `InterviewerPolicy` 和 `Rubric`：

- 技术面：正确性、复杂度、边界、技术取舍
- 行为面：STAR、个人贡献、结果证据、复盘
- 压力面：限时、连续追问、稳定性、重新组织表达
- 案例面：问题拆解、指标、假设和验证
- 科研面：研究设计、局限性、替代解释
- HR 面：动机、岗位匹配、沟通和真实性

### 算法题工作流

挑战版只支持 Python，先做 3–5 道有明确许可或自编的题目：

1. AI 让用户复述题意并确认约束。
2. 用户讲思路，AI 追问复杂度和边界情况。
3. 用户写代码或伪代码。
4. 服务端在受限环境运行固定测试用例。
5. AI 根据失败用例和代码证据给反馈，再进行一次修复。

不要把 LeetCode 原题、隐藏测试和付费题库直接复制到公开仓库。公司题频数据只保存题目链接/slug和来源说明，题干采用有许可内容或自行改写的等价题。

## 12. 远程 API、本地小模型与工作流

### 推荐的混合方案

- **远程强模型**：个性化出题、复杂追问、自然语言反馈和压力面角色扮演。
- **本地小模型或规则**：JD/简历字段抽取、技能分类、敏感信息检测、简单 rerank。
- **本地向量模型**：在有合适硬件时使用 BGE-M3 或同类中英 embedding；否则先调用远程 embedding。
- **语音识别/TTS**：挑战当天优先远程 API；本地 ASR/TTS 作为降级方案，不让它阻塞文字版闭环。
- **算法代码执行**：必须本地受限沙箱执行，不能把用户代码不加限制地交给远程服务。

如果只有 CPU 或显存不足，不建议在挑战当天强行部署 7B/8B 模型。若有约 8–12GB 以上显存，可尝试 Ollama/vLLM 部署一个 7B/8B instruct 模型，负责结构化抽取和初筛；最终反馈仍可由远程模型生成。

### 工作流拆分

```text
输入/语音
  → profile_extractor
  → job_skill_mapper
  → hybrid_retriever (GraphRAG + vector)
  → interviewer (按场景策略出题/追问)
  → answer_evaluator (rubric + 证据)
  → code_runner 或 ASR/TTS（按场景启用）
  → session_store / next_action
```

第一版用 Python 函数和状态机实现即可，不必引入复杂 Agent 框架；只要每个步骤有清晰输入、输出和失败降级，就已经是可解释的工作流。

## 13. 并行开发安排

可以拆成 3–4 个独立工作流，但先冻结共享数据契约，再并行：

1. **数据与许可**：来源台账、算法题清洗、技能 taxonomy、GraphRAG schema。
2. **面试引擎**：场景策略、Prompt、评分 rubric、会话状态机。
3. **前端与多模态**：场景选择、文本回答、录音/播放、代码编辑器和反馈卡片。
4. **部署与 QA**：API 配置、沙箱测试、公网部署、README、Demo 和 Memo。

每个线程尽量只改自己的目录；共享接口写入 `docs/contracts.md` 后再开发。最后保留一个整合线程负责合并、端到端测试和录制 Demo，避免多个线程同时改同一个 `app.py` 或前端入口文件造成冲突。
