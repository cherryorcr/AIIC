# Product Memo：AIIC 面试陪练平台

**版本**：0.1（挑战项目基线）  
**日期**：2026-08-30  
**状态**：可演示 MVP；已纳入 1 条匿名真实调研记录，但样本扩大和规模化效果仍需验证

## 1. 目标用户与核心痛点

### 1.1 目标用户

首要用户是准备实习、校招或保研面试的本科生和研究生，尤其是软件开发、算法、数据、产品和科研岗位候选人。他们通常有 JD、课程/项目经历和零散题库，但缺少一条能把“岗位要求、个人经历、面试流程和改进动作”串起来的练习路径。

根据新增匿名调研，产品用户还可以按面试组织方式分为两类：

- **单面用户**：需要独立练习某一个面试环节，或按学校/公司流程组合多个环节。已提到的环节包括简历面、专业面、论文面（科技面）、实习面、行为面和英文面。
- **群面用户**：希望与水平相近、时间重合的同学组成小组或圈子，成员能够互相看见面试表现并共同学习，而不是依赖临时寻找刚好有空的熟人。

### 1.2 证据边界

当前已有 1 条匿名真实调研摘录（记录编号 `R-001`），但它只代表一个用户的需求信号，不能推导总体比例、普遍频率或市场结论。现有证据分为四层：

| 证据 | 当前状态 | 可以支持的表述 |
| --- | --- | --- |
| 项目发起人的连续需求输入 | `observed_requirement` | 已明确希望个性化匹配、分场景模拟、算法题和统一模型路由 |
| 匿名真实调研摘录 R-001 | `observed_interview` | 支持单面/群面分类、单面环节组合、简历深挖、群面组队、录屏转写等需求信号；不代表总体比例 |
| `data/mock-survey-responses.csv` | `synthetic_mock` | 只能用于测试问卷分析和 UI 流程，不能代表真实比例 |
| 扩大后的真实访谈/问卷 | `needs_validation` | 计划访谈 5-8 人、回收 20-30 份问卷后回填并验证优先级 |

因此，本节把“已确认的需求输入”和“待验证的用户假设”分开：

- **已确认需求输入**：用户希望系统根据 JD、项目经历和技能进行岗位/题目匹配；一级入口先区分群面和单面；单面可选择或组合简历、专业、论文/科技、实习、行为、英文等环节；简历面要持续围绕简历深挖；群面要匹配水平相近且空闲时间重合的同学；自动录屏和自动转写用于复盘、提取回答证据和训练报告；技术、算法、压力、案例、科研和 HR 场景仍需有独立策略；算法题能够运行代码；业务服务、双 4090 本地模型和第三方强模型通过网关解耦。
- **待验证假设**：多环节组合是否是多数学校/公司流程；用户是否愿意提供可用于匹配的空闲时间和能力标签；录屏/转写是否被多数用户视为基础能力；群面等待池的隐私、可见范围和等待时长如何设置；用户更看重找题、判断回答质量还是连续追问。

### 1.3 真实调研摘录与初步结论

以下内容只保留匿名、与产品设计直接相关的表达；截图原文作为调研记录，不将其包装成统计结果：

| 记录 | 用户表达/场景 | 需求含义 | 置信边界 |
| --- | --- | --- | --- |
| R-001-A | “第一种是群面和单面” | 产品一级导航先区分群面/单面 | 单个样本 |
| R-001-B | “单面分为简历面、专业面、论文面（也叫科技面）、实习面、行为面、英文面”；一场学校面试可能涉及多个或全部部分 | 支持单面环节选择与组合，不能只提供一个笼统的“技术面” | 需要更多学校/公司样本 |
| R-001-C | “今天就练简历面”，希望“一直问我简历问题，把简历上所有可以挖掘的都问到” | 提供简历深挖模式、经历证据链和已问/未问覆盖状态 | 需验证全量深挖与限时训练的取舍 |
| R-001-D | 群面很难找到“水平相近且刚好同一时间有空”的多人；希望自由组队/组圈，成员面试视频互相可见并一起学习 | 按能力相似度、时间重合、人数和可见范围匹配群面参与者 | 需调查隐私、等待池和缺席处理 |
| R-001-E | “面试时自动录屏和自动转写功能是基础的” | 录屏/ASR 用于复盘、证据提取和报告生成 | 当前先做接口与数据契约，媒体链路后续实现 |

**初步产品判断**：群面不是简单的多人聊天页面，而是带能力、空闲时间、人数和可见范围约束的协同训练场景；单面不是一个统一模式，而是可组合的专业环节；录屏和转写的主要价值是复盘与证据提取，实时数字人暂不能替代真实群面匹配。

### 1.5 当前需要验证的典型场景

1. 用户拿到一份后端岗位 JD，但不知道应优先准备哪些技能和题型。
2. 用户分别练习简历面、专业面、论文/科技面、实习面、行为面或英文面，并按真实流程组合多个环节。
3. 简历面中，面试官持续深挖项目、课程和经历，系统记录已覆盖与尚未覆盖的可追问点。
4. 用户能够回答项目问题，但回答没有 STAR 结构或结果证据，无法判断如何改进。
5. 用户希望模拟面试官连续追问，而不是一次性得到一段通用答案。
6. 用户准备算法面时需要同时讲思路、分析复杂度、写代码并验证边界。
7. 用户希望参加群面，但需要匹配相似水平、空闲时间重合且人数满足的同学，并控制视频/回答的可见范围。
8. 用户希望自动录屏和转写，用于复盘、提取回答证据和生成训练报告。
9. 用户想练习压力面、案例面、科研面或 HR 面，但每种场景的评价标准不同。

### 1.6 对产品优先级的影响

- **P0（当前 MVP）**：文字单面闭环、技术/算法/行为/压力等场景策略、算法题执行、岗位与题目匹配、原句证据反馈、追问和重答。
- **P1（下一迭代）**：简历深挖模式、可组合单面流程、群面匹配等待池、群面房间与成员状态、录屏/转写接口设计和复盘数据模型。
- **P2（后续产品路线）**：浏览器录屏、ASR 转写、多人实时房间、媒体复盘和可控的视频可见范围；实时数字人作为独立验证项，不替代真实群面匹配。

## 3. 版本迭代记录

### V0：最初构想

最初方案是一个能够收集真实面试数据、结合用户个性化背景，通过 GraphRAG 匹配目标岗位和推荐面试题，并模拟多种面试流程的 AI 面试官。早期设想还包含实时数字人、语音和视频，以及把所有服务都接到远程 API。

### V0 → V0.1：范围收敛

**问题**：在一天内同时完成多模态、数字人、数据采集、GraphRAG、算法执行和多种面试策略，交付风险过高。  
**改动**：将文字面试、算法题、岗位/技能匹配、结构化反馈和场景策略设为核心；语音、视频和数字人保留扩展接口。  
**原因**：先证明“岗位/个人证据 → 题目 → 回答 → 反馈”的闭环，再扩大交互形态。

### V0.1：从“全远程 API”改为混合模型架构

**问题**：所有抽取、向量和评分都调用强模型会带来成本、延迟、供应商不可用和隐私风险。  
**改动**：业务服务部署在 CPU 云服务器；双 RTX 4090 通过 OpenAI-compatible 网关提供本地模型；复杂生成和长反馈才路由第三方强模型；所有业务调用经过 `ModelRouter`。  
**原因**：把供应商依赖集中在一处，支持 fallback、成本统计和后续替换。

### V0.1：从“抓真实题库”改为来源治理 + 许可转写

**问题**：公开面经的版权、隐私和“高频”真实性难以证明；未授权题库不能直接复制到公开仓库。  
**改动**：活动数据使用已核验的 MIT 来源元数据；算法和系统设计题使用基于主题的自行转写；所有数据登记 URL、许可证、版本、访问时间、脱敏和置信度；模拟数据保留 `synthetic_mock` 标记。  
**原因**：让数据可公开演示、可追溯且不误导用户。

### V0.1：从“只生成问题”改为“问题 + 原句证据反馈 + 可重答”

**问题**：一次性生成问题和参考答案无法告诉用户具体哪里不足。  
**改动**：为每个场景定义 Rubric；反馈必须包含原句证据、优点、改进、改进后的回答结构和下一步动作；支持 `revision_of` 重答。  
**原因**：反馈的可执行性是区别于直接使用通用 ChatGPT 的关键待验证价值。

### V0.1：从“直接执行代码”改为受限沙箱

**问题**：用户提交的 Python 代码可能访问网络、文件系统或消耗无限资源。  
**改动**：增加 AST 规则、audit hook、受限子进程、测试 harness、超时和资源上限；明确公网开放前必须迁移独立 runner。  
**原因**：算法题是产品核心场景，但安全边界不能被忽略。

## 4. 一周后续设计

### 第 1-2 天：真实研究和问题校准

- 完成 5-8 个半结构化访谈，覆盖大三/大四、研一/研二、开发/算法/科研方向。
- 回收 20-30 份匿名问卷，标注最近面试时间、场景和实际准备步骤。
- 对访谈原话做主题编码，区分痛点频次、严重度和付费/使用意愿。

### 第 3 天：数据和评测集

- 建立 5 组脱敏 JD、5 组用户背景和 20-30 道有许可/自编题。
- 为岗位技能、题目技能、场景和 Rubric 做人工金标准。
- 评估岗位匹配准确率、题目相关性、证据引用率、编造率和追问相关性。

### 第 4 天：面试引擎和反馈质量

- 将每个场景的 Prompt、Rubric 和失败示例版本化。
- 增加人工复核界面，支持标记“事实错误”“证据缺失”“建议不可执行”。
- 引入结构化输出重试、敏感信息检测和回答原文最小化保存策略。

### 第 5 天：模型和成本优化

- 用相同评测集对双 4090 本地模型、第三方强模型和规则 fallback 做对比。
- 记录 p50/p95 延迟、超时率、token、成本和质量分。
- 依据结果确定“本地优先”任务和“强模型优先”任务。

### 第 6 天：部署与安全

- 将 Redis/worker 和独立 sandbox runner 加入 Compose。
- GPU 网关启用 API key、私网绑定或 mTLS；完成重启、回滚和备份恢复演练。
- 对上传文件、会话 Cookie、管理员 API 和算法沙箱做攻击面检查。

### 第 7 天：用户验证与发布

- 让真实用户完成一轮训练，记录完成率、卡点、主观价值和是否愿意再次使用。
- 修复最高影响的 3 个问题，更新 Product Memo、README、Demo 和验收结果。

## 5. AI 工具使用

以下记录描述本项目中的工具类别和使用环节；具体供应商、模型版本和密钥应以部署环境变量及提交记录为准。

| AI 工具/能力 | 使用环节 | 产出 | 人工责任 |
| --- | --- | --- | --- |
| ChatGPT/Codex 类强模型 | 需求梳理、Product Memo 草拟、复杂回答反馈、文档整理 | 方案草稿、反馈文本、文档初稿 | 核对实现、事实、范围和隐私边界 |
| 本地 Qwen/vLLM 模型 | JD/简历抽取、轻量出题、结构化 fallback | JSON 抽取、候选问题 | 校验 schema、质量和显存/延迟 |
| Embedding/Reranker | 技能和题目语义召回 | 相似度和排序信号 | 评估召回质量，保留规则 fallback |
| GitHub API/网页阅读 | 核验公开题库来源和 MIT 许可 | 来源 URL、版本和许可证元数据 | 判断是否允许转写/再分发 |
| Codex 文档/代码工具 | 代码阅读、接口梳理、文档生成和 QA | Markdown、DOCX、测试与审计结果 | 最终审阅、运行验证和发布 |

AI 不是事实来源。任何 AI 生成的用户经历、面试频次、来源许可或评测结论都必须人工核验；模型调用日志不应包含 API key 和未脱敏个人材料。

## 6. 成功标准

- 至少 5 名真实目标用户完成一轮训练，4/5 能独立完成。
- 3/5 用户认为反馈比直接使用通用 ChatGPT 更具体。
- 每条反馈至少包含一条可定位的回答原句和一条可执行改进。
- 题目详情可追溯技能、场景、来源类型、许可证和版本。
- 模型失败、算法超时和用户重答都不会丢失输入。

## 7. 尚未解决的问题

1. 真实用户最看重的场景尚未通过访谈验证。
2. 题目推荐和反馈质量尚无足够人工金标准。
3. 第三方强模型的额度、数据保留和服务稳定性依赖实际合同/服务条款。
4. 当前算法沙箱适合挑战演示，尚不应直接承载不受信任的公网代码执行。
5. 当前正式账户缺少邮件验证、找回密码和 OAuth 生命周期能力。
